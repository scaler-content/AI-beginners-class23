Console Orientation, Regions & the $0 Billing Alarm

⏱ 14 min

Before creating a single resource, set a tripwire that emails you the moment real spend appears. Every class from here builds on top of this being done first, always.

🛠 Instructor Does — live, on screen, 3 min

Walk the room through the console's three fixed landmarks: the region selector (top right — most services are region-scoped, meaning a resource created in Mumbai is invisible from N. Virginia's view), the search bar (the fastest way to reach any service by name instead of hunting menus), and the account name menu (top right, next to region — this is where Billing lives). Say clearly: today's resources go in one consistent region, chosen once, in §2.

Why a billing alarm has to exist before anything else

Nothing about the free tier stops a misconfigured resource from silently billing real money once a cap is crossed — there's no gentle warning banner the way Render's dashboard shows one. A billing alarm is the only thing standing between "oops" and "found out three weeks later." AWS actually offers two different tools for this, and it's worth knowing both exist.

ToolWhat it actually doesThe gotcha
AWS BudgetsLets you set a literal near-zero dollar threshold (e.g. "alert me the moment actual spend crosses $1") and emails you when it's crossed. The more direct match for "a $0 alert."Found under Billing and Cost Management — no region-switching needed, it's account-wide.
CloudWatch billing alarmThe older, more commonly tutorialized route — a CloudWatch alarm watching the account's EstimatedCharges metric.The metric is only ever published in us-east-1 (N. Virginia) — an alarm created in any other region will sit there silently and never fire, no matter what actually gets spent.
✅ Do This Live — Set Up a Near-Zero Spend Alert (AWS Budgets route)
  1. Open the account menu (top right) → Billing and Cost Management.
  2. In the left sidebar, first open Billing preferences and check "Receive Billing Alerts" (some accounts also show a Free Tier usage alert checkbox — check that too) → Save preferences. Billing alarms of either kind silently do nothing until this box is checked.
  3. Go to Budgets → Create a budget → choose a Zero spend budget template if offered, or a Cost budget with a $1 monthly threshold otherwise.
  4. Set an alert threshold at 100% of actual spend and enter your own email as the recipient.
  5. Create the budget, then open the confirmation email AWS sends and confirm the subscription — nothing arrives later without this click.
The classic gotcha, taught on purpose: if you (or a student) instead follow an older tutorial's CloudWatch-alarm route, the alarm has to be created with the region selector set to US East (N. Virginia) / us-east-1 — even if every resource today lives in Mumbai or anywhere else. This is a genuinely common trip-up; verify it's still accurate the night before teaching, since AWS documentation has shifted emphasis toward Budgets over the years.

IAM Hands-On — Creating a Scoped, Non-Root User

⏱ 14 min

Class 22 explained least privilege. Today Nikhil actually clicks through creating the user who'll do every remaining step today — never root again after this section.

Say this before Step 1: the root user (the identity created at signup) can do literally anything, including deleting the whole account. AWS's own guidance is to stop using it for daily work immediately after setup. Everything from here — S3, Elastic Beanstalk, EC2 — should be done signed in as the IAM user created below, not root.
✅ Do This Live — Create the Deploy User
  1. Console search bar → IAM → Users (left sidebar) → Create user.
  2. Name it something identifiable, e.g. nikhil-deploy. Check "Provide user access to the AWS Management Console" so it can be verified by logging in as this user today — choose "I want to create an IAM user" and set a custom password (uncheck "require password reset" for classroom speed).
  3. On the permissions screen, choose "Attach policies directly". For today's work, search for and attach: AmazonS3FullAccess, AWSElasticBeanstalkFullAccess, and AmazonEC2FullAccess.
  4. Review and Create user. Note the IAM sign-in link shown on the confirmation screen (format: https://[account-id-or-alias].signin.aws.amazon.com/console) — this, not the root email, is how you'll sign back in for every remaining step today.
  5. Sign out of root. Sign back in via that IAM sign-in link with the new username and password, and confirm the console loads — this is the checkpoint that actually proves the user works.
Say this out loud, honestly: the three managed policies above are broad — AmazonS3FullAccess grants access to every bucket in the account, not just today's demo bucket. That's a deliberate classroom trade-off for speed, not real least privilege. A production setup would instead write a custom JSON policy scoped to exact actions on exact resource ARNs — SIM 2 below is exactly that exercise, without touching the real console.

S3 Hands-On — Bucket, Upload & the Public-Access Trap

⏱ 14 min

Object storage as a building block, hands-on — and the one real behavior change that catches almost everyone who last touched S3 more than a couple of years ago.

✅ Do This Live — Create a Bucket and Upload a File
  1. Signed in as nikhil-deploy, console search → S3 → Create bucket.
  2. Bucket names are globally unique across all of AWS — pick something specific, e.g. blurbbot-demo-yourname-2026. Choose the same region today's other resources will use (§5–§6 pick one region and stick with it).
  3. Leave every Block Public Access setting checked on — this is the correct default, and stays that way for the bucket as a whole.
  4. Create bucket, open it, Upload → Add files, pick any small test file, and upload.
  5. Click the uploaded object's name → copy its Object URL → open it in a new browser tab. Expect Access Denied — that's Block Public Access doing exactly its job.
Not the old 2018 behavior — say this explicitly: S3 now blocks all public access by default on every new bucket, account-wide. Older tutorials that show one checkbox toggle to "make public" are describing pre-2023 defaults. Getting one object public today genuinely requires two separate steps, on purpose — AWS added the friction after a long string of real-world leaked-bucket incidents.
✅ Do This Live — Make Exactly One Object Public (Not the Whole Bucket)
  1. Bucket → Permissions tab → Block public access (bucket settings) → Edit → uncheck only "Block public access to buckets and objects granted through new public bucket or access point policies" → save, type confirm.
  2. Back in Permissions, scroll to Bucket policy → Edit, and paste a policy granting s3:GetObject to * scoped to only that one object's ARN — not arn:aws:s3:::bucket-name/*, which would expose everything in the bucket.
  3. Save, return to the object, copy its Object URL again, and reopen it — it should now resolve instead of Access Denied.
Security callout — say this with real weight, not as a footnote: a bucket policy scoped to /* instead of one specific object key is the single most common way real S3 leaks happen — member lists, invoice PDFs, backup dumps, all reachable by anyone with the URL. Scope every public grant to the exact object it needs to cover, never the whole bucket, especially once real customer data like the chain's member records is involved.

Meet Blurb Bot — The One App Both Paths Deploy

⏱ 8 min

One form field, one AI call, one page. Small enough to write live, small enough to deploy twice, and it closes a loop that's been open since Class 17.

🎙 Instructor Says

"Remember shelf-talker.html from Class 17 — the one that only ever worked by double-clicking it on Nikhil's own laptop? Blurb Bot is its real successor: type a book title, get back a one-line shelf-talker blurb generated live by an actual LLM call, on a page anyone can reach — not just whoever's standing at Nikhil's desk. Same idea from Class 17, finally running on real infrastructure with a real address."

Which LLM, and why: Blurb Bot calls Groq's API — the same reliable free choice this series settled on back in Class 16, after Gemini's free tier proved too rate-limit-prone for a live class. Groq's API is OpenAI-compatible (same request shape, different base URL) and its free tier needs no card on file for the API itself — a real, currently-available free tier with per-model request-per-minute and token-per-minute caps, not a time-limited trial. Model used below: llama-3.1-8b-instant — fast, currently listed as a production model, and more than enough for a one-line blurb.

app.py — the whole backend

from flask import Flask, render_template, request
import os
from openai import OpenAI

app = Flask(__name__)
client = OpenAI(
    api_key=os.environ.get("GROQ_API_KEY"),
    base_url="https://api.groq.com/openai/v1"
)

@app.route("/", methods=["GET", "POST"])
def index():
    blurb = None
    title = ""
    if request.method == "POST":
        title = request.form.get("title", "").strip()
        if title:
            resp = client.chat.completions.create(
                model="llama-3.1-8b-instant",
                messages=[
                    {"role": "system", "content": "Write one punchy one-line bookshop shelf-talker blurb for the given title. Under 20 words. No surrounding quotes."},
                    {"role": "user", "content": title}
                ],
                max_tokens=60
            )
            blurb = resp.choices[0].message.content.strip()
    return render_template("index.html", blurb=blurb, title=title)

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=8000)

Path A — Elastic Beanstalk (Beginner Path)

⏱ 20 min

Hand AWS the code; it provisions and manages the EC2 machine, load balancer, and health checks underneath. Fewer decisions, one command to go live.

Before Step 1 — Confirm the EB CLI Is Installed

Check · Python installed?Run python3 --version (Mac) or python --version (Windows). The EB CLI installs via pip, so Python has to already be there — install from python.org first if it's missing.
Install, on MacRun python3 -m pip install --upgrade --user awsebcli in Terminal. If eb isn't recognized afterward, the pip user-install path isn't on PATH yet — the terminal output tells you exactly which folder to add.
Install, on WindowsOpen a fresh Command Prompt or PowerShell and run pip install awsebcli --upgrade --user. If eb --version fails afterward, add the Python Scripts folder shown in the install output to your system PATH and reopen the terminal.
Confirm either OSRun eb --version — a version string back means it's ready.
✅ Do This Live — Deploy Blurb Bot via Elastic Beanstalk
  1. In the Blurb Bot project folder (containing app.py, requirements.txt, templates/), run eb init. Choose your region, an application name (e.g. blurb-bot), and the Python platform matching your local version.
  2. When prompted for credentials, use the access key of nikhil-deploy from §2 — generate one under that IAM user's Security credentials tab if it doesn't already have one. Never the root account's keys.
  3. Run eb create blurb-bot-env. This provisions an EC2 instance, a load balancer, and health monitoring underneath — expect several minutes, not instant.
  4. Checkpoint: once it finishes, run eb status — it should read Health: Green before continuing.
  5. Set the Groq key without ever touching a file: eb setenv GROQ_API_KEY=your_actual_key_here.
  6. Run eb open — it opens the live EB URL in a browser. Type a book title into Blurb Bot and confirm a real blurb comes back.
Flag this honestly: modern Elastic Beanstalk Python platforms (Amazon Linux 2023) generally expect a Procfile in the project root (one line: web: gunicorn app:app) to know how to start the app — older platform generations auto-detected an application.py file instead. Confirm which platform generation is current and which file EB expects the night before you teach this; EB's exact auto-detection behavior is one of the more actively-changing corners of AWS's docs.
Checkpoint recap: three green checkpoints, in order — eb create finishes without error, eb status reads Health: Green, and eb open loads a page that actually returns a blurb. Any red between those is worth pausing on before moving to Path B.
§ 5

Path B — EC2 + EC2 Instance Connect (Intermediate Path)

⏱ 20 min

The same app, the manual way — full control over the machine, and a browser-based connection with no local SSH key setup at all.

Instance-type honesty check, before Step 1: the classic "750 free EC2 hours a month, 12 months" claim applies only to accounts created before July 15, 2025 (see §Setup). Confirm live which free-tier terms today's demo account is actually on, and pick a genuinely free-tier-eligible size for it — t2.micro or t3.micro on the classic tier, or a small size covered by remaining credit on a newer account. Re-verify the current list at aws.amazon.com/free before class.
✅ Do This Live — Launch, Connect, and Run Blurb Bot on EC2
  1. Console search → EC2 → Launch instance. Name it (e.g. blurb-bot-ec2), choose the Amazon Linux AMI, and instance type t3.micro (or t2.micro — whichever your account's free tier actually covers).
  2. Key pair: select "Proceed without a key pair" — EC2 Instance Connect below needs no local SSH key at all.
  3. Network settings → Edit: allow SSH (port 22) from My IP, and add a second custom TCP rule opening port 8000 (Blurb Bot's port) from Anywhere (0.0.0.0/0) — that second rule is what makes the live URL publicly reachable.
  4. Launch instance, wait for its status to read Running and 2/2 checks passed.
  5. Select the instance → Connect → the EC2 Instance Connect tab → Connect. A browser-based terminal opens directly — no local .pem file, no ssh command typed anywhere.
  6. In that browser terminal: sudo yum install -y python3-pip git, then git clone the Blurb Bot repo, cd into it, pip3 install -r requirements.txt --user.
  7. Set the key for this session and run it: export GROQ_API_KEY=your_actual_key_here then python3 app.py. Keep this terminal open — closing it stops the app.
  8. Checkpoint: copy the instance's Public IPv4 address from the EC2 console, open http://that-address:8000 in a browser, and confirm Blurb Bot actually returns a blurb end to end.
Kept deliberately minimal, on purpose: Flask's own built-in server (app.run(...)) is doing the serving here, not gunicorn behind nginx — that stack is real-world best practice, but it's more moving parts than a live two-hour class needs to get one working public URL. Say this out loud as a scope call, not an oversight.
Opening 0.0.0.0/0 on a custom port is a classroom trade-off, said honestly: it's the fastest way to get a demo-reliable public URL live in one session. A real deployment would restrict that rule far more tightly (a specific IP range, or better, behind a load balancer) — flag this out loud as a shortcut being taken for demo reliability, not a recommended production pattern.

Which Path, When — The Real Decision Framework

⏱ 12 min

Both paths just deployed the exact same app. The choice between them was never about capability — it's about how much of the machine underneath you actually want to manage yourself.

QuestionPoints toward Elastic BeanstalkPoints toward EC2
Who's doing this deploy?Someone deploying solo, wants a URL back fast.Someone who wants to see and control every layer themselves.
Does the app need custom OS-level setup?No — a standard Python platform covers it.Yes — a specific package, service, or config EB's platform doesn't offer directly.
Who patches and scales the underlying server?AWS, automatically, as part of the platform.You — full control, full responsibility.
Time budget to a working URL?Minutes — a handful of eb commands.Longer — every install step is manual, on purpose.

§ 7

Cleanup & Free-Tier Monitoring — Avoiding the Surprise Bill

⏱ 12 min

This is the section that keeps today free, literally. Treat it with the same weight as the deploy itself — an unattended resource is how a free class becomes a real bill.

✅ Do This Live — Tear Down Everything Built Today
  1. EC2: Instances → select blurb-bot-ec2 → Instance state → Terminate instance. Terminate, not just Stop — a stopped instance can still hold billable storage attached to it.
  2. Elastic Beanstalk: run eb terminate blurb-bot-env, or console → environment → Environment actions → Terminate environment.
  3. Don't stop there: Elastic Beanstalk auto-creates its own S3 bucket to hold uploaded application versions and logs — terminating the environment does not delete that bucket. Check S3 for a bucket named like elasticbeanstalk-[region]-[account-id] and remove it manually if it's not needed.
  4. Delete the demo bucket created in §3 as well — empty it first if it holds more than one object.
  5. Recheck the Billing dashboard (or the Budget created in §1) the next day, not immediately — billing data has a reporting delay, so "$0 right now" isn't proof yet.
Say this with real weight: "terminated the environment" and "done" are not the same sentence. The single most common real AWS surprise-bill story is exactly this shape — an environment or instance gets torn down, but a bucket, an Elastic IP, or a log group it created along the way keeps quietly running. Five extra minutes checking S3 and EC2 directly is the actual difference between a free class and a bill nobody expected.

Key Takeaways

1. The billing alarm comes first, always — before the first resource, not after. A $1 Budget alert or a correctly-regioned CloudWatch alarm is the only real safety net a free-tier class has.

2. Root is for setup, not for daily work. The very first real action on a new AWS account should be creating a scoped IAM user and never touching root again.

3. S3 defaults to private now, on purpose. Public access takes two deliberate steps — and should be scoped to one object, never a whole bucket, especially once real data is involved.

4. Elastic Beanstalk and EC2 deployed the identical app today — the difference was never capability. It's how much of the machine underneath you want to manage yourself.

5. "Terminated" and "cleaned up" are not the same word. Check what an environment or instance quietly created along the way before calling cleanup done.
